# Physical iPhone foreground connection implementation plan

> **For agentic workers:** REQUIRED SUB-SKILL: Use superpowers:executing-plans to implement this plan task-by-task.

**Goal:** Pair the native companion with one owned, authenticated managed Codex host over private HTTPS, then repeat the real question/reply flow on the selected physical iPhone.

**Architecture:** Keep the existing authenticated loopback bridge and immutable control/operation protocol. Put only the explicitly owned bridge listener behind a bounded Tailscale Serve HTTPS route; retain the bearer capability inside the iPhone's Keychain. The unsigned DEBUG Simulator uses an injected in-memory credential store plus its existing private development file; no real Keychain assumption is needed there. Pairing is a deliberate host-address/connection-key form, not a token-bearing URL or a transcript push. This is the physical-transport prerequisite for the subsequent APNs slice, not push implementation itself.

**Tech Stack:** Existing Python/Node bridge, Tailscale Serve, SwiftUI/Foundation/Security; local Xcode signing and devicectl. No hosted CI, dependencies or public relay.

**Spec:** docs/companion-v1-design.md. Native wire contract: bridge/README.md. Preceding Simulator outcome: docs/native-client-progress.md.

## Global constraints

- No existing/shared Codex sessions; retain owned managed launch, upstream capability authentication, quiet-launch readback and environment scrub for every trial.
- No public Funnel, global Tailscale resets, shared listener replacement, certificate-validation bypass, new DNS, subscription or cloud key creation in this slice.
- Private-network listener exposure is a separate concrete validation action; prepare and review implementation first, then settle exact narrow exposure authorization before enabling it. Preserve any existing Serve mappings. Local edits/tests do not depend on that action.
- Signed device builds require an explicit app bundle ID on the already-installed sole team, but do not infer that existing profiles match: current read-only check found one signing identity/team, zero matching companion/push profiles. Prepare the build first; automatic signing/provisioning requires a concrete authorization naming this exact bundle ID and installed team before persistent Apple-account updates. Confirm the team supports APNs before selecting it; an installed certificate alone does not establish paid-program membership. Only read-only signing inspection before that gate; user-only account/TCC/device prompts are genuine handoffs. Never request or print credentials.
- One available paired iPhone was observed by devicectl. Re-resolve the selected device immediately before install; do not act on other records or assume a physical test passed from a Simulator run. No raw device inventory in reports.
- APNs registration, provider keys, entitlements and notification permission remain a separately reviewed next slice. Do not promise locked-device push from private foreground HTTP.

## Review focus

1. Pairing with a wrong/unreachable host must never enable stale controls or send an old answer to a newly paired host.
2. HTTPS redirects, auth challenges, proxy settings, invalid URLs and token control characters must not leak a capability.
3. Keychain denial/locked device and partial replacement must fail closed with useful status, never fall back to plaintext app storage.
4. An existing or concurrently changed Serve mapping must be preserved; stop/crash/timeout cleanup must touch only a demonstrably owned route.
5. Phone network loss and foreground transitions must preserve uncertain outcomes and require current authoritative state before answering.

## Sources and known access gates

Tailscale Serve is private to the tailnet and supports HTTPS reverse proxying; HTTPS enablement can require a user admin action. Existing Serve has one listener, so configuration preservation is mandatory: https://tailscale.com/docs/reference/tailscale-cli/serve and https://tailscale.com/docs/features/tailscale-serve.

Subsequent actual APNs delivery requires app registration/appropriate signing entitlement and provider authentication. Existing signing alone proves none of those; do not look for arbitrary private keys. References: https://developer.apple.com/documentation/usernotifications/registering-your-app-with-apns and https://developer.apple.com/help/account/capabilities/communicate-with-apns-using-authentication-tokens/.

## Review rulings

Failed credential replacement uses a deliberately stricter fail-closed transaction: previous item is preserved but no previous client remains writable or silently reconnects. An explicit retry can restore that identified prior host through a fresh GET. This resolves both review lanes' consistency concerns without assuming storage writes or deletion succeeded.

Installed version-matched Serve source establishes ETag plus foreground-session ownership; no port-wide off action is needed. The route supervisor plus launcher independently enforce the operational deadline and single-watcher failure handling; watcher teardown caller is retained. Simultaneous watcher death or unacknowledged startup failure needs operator cleanup, so no hard deadline is claimed for that residual. Upstream server/amx crash cleanup remains best effort; do not conflate it with a route that can reach the phone.
